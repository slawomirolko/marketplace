# olko-implementation-closure

Load in step 11 of `olko-implementation-orchestrator`, after the merge. Steps 11a and 11b run only after the last Task of a Feature.

## Adaptation
1. Read `.agents/skill-config.md` when present.
2. If `projectAdapter` is not `false`, load `.agents/skills/olko-implementation-closure/project.md` when present.
3. Apply rules in this order: Configuration, Project Adapter, AGENTS.md, then this skill.

## Procedure

Before deleting the Task technical plan in Step 11, copy its final implementation journal, Task review, runtime/log/trace/DB evidence, PR, and merge details into the persistent Feature delivery tracker. The Feature tracker is the durable record after Task-plan cleanup; never delete it during Task cleanup.

11. POST-MERGE: run this step from the MAIN checkout. First, journal that you will use the REAL main Compose project. Rebuild and verify the merged code with the real project name, containers, and ports. Do not use the worktree override or port offset. Confirm that this is the project that received the merge, then record the evidence. Before finishing, confirm that no isolated worktree project or volumes remain. Tear down any that remain. After verification passes, remove only this Task's exact implementation plan file (for example, `plans/features/<feature-id>/tasks/<task-id>-implementation.md`). Every Task must have this file before implementation; if it is missing, return to Feature planning rather than proceeding. Never delete `business.md`, `feature-tracker.md`, another Task's plan, or any containing directory at this step; Feature-level files are removed only through the approved whole-Feature cleanup in step 11b. If the file path is ambiguous, retain it and report the ambiguity. This post-merge deletion is authorized by the flow; do not ask for a second approval.
11a. FEATURE COMPLETION AUDIT (MANDATORY, ONCE, AFTER THE LAST TASK): after post-merge verification, read the owning Feature and all child Tasks from YouTrack and the shared Feature delivery tracker. Run this step only when every child Task is merged and has a passing Task review (step 7c) and post-merge verification. If any Task is open, blocked, lacks evidence, or failed, record `FEATURE_AUDIT_PENDING` with the missing items and stop; never claim Feature completion. When ready, capture the Feature base commit (recorded before the first Task PR) and current main commit. Audit the cumulative Task PR merge commits; use `base..HEAD` only when it contains no unrelated mainline changes. Run each applicable stack auditor once over that combined scope and the full Feature acceptance criteria. Ask the auditors to focus on cross-Task integration, shared contracts/domain models, regressions, completeness, and end-to-end acceptance; do not repeat individual Task reviews. Run the Feature's end-to-end acceptance/runtime checks and inspect logs/traces/DB evidence across the combined behavior. Record all audit evidence and a final `PASS` / `FAIL` in the shared Feature delivery tracker. Only `PASS` permits marking the Feature complete. On `FAIL`, identify affected Task(s), create or revise the corrective Task through the approved backlog workflow, deliver it as its own PR with the full Task review gate (step 7c), then rerun this Feature audit after that PR merges. Retain the shared Feature delivery tracker and every Feature-level plan through the audit; Task cleanup never removes them. Feature-level file removal is governed by step 11b and requires the user's explicit approval.
11b. FEATURE PLAN-FILE CLEANUP (ASK FIRST; ONLY FOR THE LAST TASK, ONLY AFTER A PASSING FEATURE AUDIT): when step 11a recorded `PASS` for a Feature with no remaining child Task work, ask the user whether to remove all files regarding that Feature — the whole Feature plan directory (for example `plans/features/<feature-id>/` or `plans/<feature-id>/`), meaning the Feature business plan, technical/implementation plan, stack plan, every remaining Task plan, and the shared Feature delivery tracker. Before asking, list the exact absolute paths and state what disappears with them: the Feature base commit, the ordered Task/PR list, the Task reviews, the post-merge runtime evidence, and the final audit verdict. Never delete these files on your own initiative; never delete them when the audit is `PENDING`, `FAIL`, or blocked; and never delete only part of the directory without the user naming exactly which paths. This step is the ONLY authorization to delete Feature-level files. On explicit approval, first copy the closure record (base and final commits, Task/PR list, audit verdict, YouTrack states) into the owning Feature issue in YouTrack, then delete exactly the named Feature directory, confirm it is gone, and report the approval and the removed paths. If approval is declined or never given in the session, retain everything and record the decision as `DECLINED`.
