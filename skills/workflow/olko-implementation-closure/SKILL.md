# olko-implementation-closure

Load in step 11 of `olko-implementation-orchestrator`, after the merge. Run step 11 (acceptance E2E), then step 12 (main-stack runtime). Steps 12a and 12b run only after the last Task of a Feature and always before step 13. Step 13 (cleanup) runs last: its worktree removal is the final filesystem action of the Task lifecycle, and it may run only after the session has been relocated out of the Task worktree.

## Adaptation
1. Read `.agents/skill-config.md` when present.
2. If `projectAdapter` is not `false`, load `.agents/skills/olko-implementation-closure/project.md` when present.
3. Apply rules in this order: Configuration, Project Adapter, AGENTS.md, then this skill.
4. Read `postMergeE2E` from `.agents/skill-config.md`. Default is `required`. Only an explicit `off` skips step 11, and that decision must be recorded in the journal and tracker.

## Procedure

Run order is numeric: 11, 12, then 12a and 12b on the last Task of a Feature, then 13 as the final step. Never remove the Task worktree before 12a and 12b finish, and never remove it while any session still resolves that directory as its project root.

11. POST-MERGE ACCEPTANCE E2E (MANDATORY, BEFORE WORKTREE REMOVAL): after `merge-retain` returns the merge commit with the Task worktree retained, create a separate disposable checkout at `<newMainSha>` and delegate `olko-e2e-acceptance-runner` with the approved acceptance-to-E2E matrix, manifest, Task ID/URL, target SHA, checkout path, and a report directory under the system temp directory. Use a unique Compose project and project-scoped database and volumes; reject shared or externally named volumes and shared container names. `PASS` requires every criterion to pass, raw and annotated screenshots uploaded to the Task, and verified cleanup of the checkout, Compose project, database records, networks, and volumes. Never mark tests skipped or reuse a prior run. On `FAIL` or `NOT VERIFIED`, retain the Task worktree and plan, report the first actionable failure, and stop before cleanup.
12. POST-MERGE RUNTIME: run this step from the MAIN checkout only after step 11 passes. First, journal that you will use the REAL main Compose project. Rebuild and verify the merged code with the real project name, containers, and ports. Do not use the worktree override or port offset. Do not run acceptance scenarios against shared development data. Confirm that this is the project that received the merge, then record the merge SHA and evidence. If it fails, retain the Task worktree and plan.
12a. FEATURE COMPLETION AUDIT (MANDATORY, ONCE, AFTER THE LAST TASK): after post-merge verification, read the owning Feature and all child Tasks from YouTrack and the shared Feature delivery tracker. Run this step only when every child Task is merged and has a passing Task review (step 7c) and post-merge verification. If any Task is open, blocked, lacks evidence, or failed, record `FEATURE_AUDIT_PENDING` with the missing items and stop; never claim Feature completion. When ready, capture the Feature base commit (recorded before the first Task PR) and current main commit. Audit the cumulative Task PR merge commits; use `base..HEAD` only when it contains no unrelated mainline changes. Run each applicable stack auditor once over that combined scope and the full Feature acceptance criteria. Ask the auditors to focus on cross-Task integration, shared contracts/domain models, regressions, completeness, and end-to-end acceptance; do not repeat individual Task reviews. Run the Feature's end-to-end acceptance/runtime checks and inspect logs/traces/DB evidence across the combined behavior. Record all audit evidence and a final `PASS` / `FAIL` in the shared Feature delivery tracker. Only `PASS` permits marking the Feature complete. On `FAIL`, identify affected Task(s), create or revise the corrective Task through the approved backlog workflow, deliver it as its own PR with the full Task review gate (step 7c), then rerun this Feature audit after that PR merges. Retain the shared Feature delivery tracker and every Feature-level plan through the audit; Task cleanup never removes them. Feature-level file removal is governed by step 12b and requires the user's explicit approval.
12b. FEATURE PLAN-FILE CLEANUP (ASK FIRST; ONLY FOR THE LAST TASK, ONLY AFTER A PASSING FEATURE AUDIT): when step 12a recorded `PASS` for a Feature with no remaining child Task work, ask the user whether to remove all files regarding that Feature — the whole Feature plan directory (for example `plans/features/<feature-id>/` or `plans/<feature-id>/`), meaning the Feature business plan, technical/implementation plan, stack plan, every remaining Task plan, and the shared Feature delivery tracker. Before asking, list the exact absolute paths and state what disappears with them: the Feature base commit, the ordered Task/PR list, the Task reviews, the post-merge runtime evidence, and the final audit verdict. Never delete these files on your own initiative; never delete them when the audit is `PENDING`, `FAIL`, or blocked; and never delete only part of the directory without the user naming exactly which paths. This step is the ONLY authorization to delete Feature-level files. On explicit approval, first copy the closure record (base and final commits, Task/PR list, audit verdict, YouTrack states) into the owning Feature issue, then delete exactly the named Feature directory, confirm it is gone, and report the approval and the removed paths. If approval is declined or never given in the session, retain everything and record the decision as `DECLINED`.
13. CLEANUP (FINAL STEP; WORKTREE REMOVAL IS THE LAST FILESYSTEM ACTION): run only after steps 11 and 12 pass and, on the last Task of a Feature, after 12a and 12b are closed. Then follow this order exactly; never reorder 13a, 13b, and 13c.
  - 13a. FINALIZE EVERY DURABLE RECORD FROM THE MAIN CHECKOUT, before anything is removed: copy the final implementation journal, Task review, runtime/log/trace/DB evidence, PR, and merge details into the persistent Feature delivery tracker; persist agent memory. Then remove only this Task's exact implementation plan file (for example, `plans/features/<feature-id>/tasks/<task-id>-implementation.md`). Every Task must have this file before implementation; if it is missing, return to Feature planning rather than proceeding. Never delete `business.md`, `feature-tracker.md`, another Task's plan, or any containing directory at this step; Feature-level files are removed only through the approved whole-Feature cleanup in step 12b. If the file path is ambiguous, retain it and report the ambiguity. This post-merge deletion is authorized by the flow; do not ask for a second approval.
  - 13b. RELOCATE THE SESSION OUT OF THE TASK WORKTREE (MANDATORY, BEFORE REMOVAL): the orchestrator session and every child session inherit the Task worktree as their project directory, and the runtime resolves `.opencode/agents`, `.agents/skills`, and project configuration relative to that directory. Removing the worktree while a session still lives in it empties that session's agent registry, fails the drain with `Session.AgentNotFoundError: Agent not found: "<agent>"`, and leaves the session permanently unusable (`404` on prompt and diff). Before any removal, move the orchestrator session to `mainRepoPath` with the runtime's session-move capability (`opencode.session_move`; HTTP `POST /api/session/{sessionID}/move` with `{"directory": "<mainRepoPath>"}`), then verify both facts: the session's project directory now resolves to `mainRepoPath`, and `<mainRepoPath>/.opencode/agents/olko-implementation-orchestrator.md` exists. Never attempt this after the directory is gone, and never assume a child inherits the relocated directory without re-checking.
  - 13c. DELEGATE THE REMOVAL ONLY AFTER 13a AND 13b: pass phase `cleanup-after-e2e` to `olko-worktree-lifecycle-manager` with `mainRepoPath`, the exact disposable E2E checkout path, the exact Task worktree path, and an explicit `session-relocated: <current session directory>` attestation. It removes the disposable E2E checkout and its Compose resources first, then the Task worktree as its final action. If any surviving session still resolves the worktree as its project root, do not remove it; report the blocker instead.
  - FALLBACK when the runtime cannot move a session: stop at `cleanup-ready`, do not remove the worktree, report the exact worktree path, branch, and removal command, and state that the user must run the removal from a session opened in the main checkout.
  - If any cleanup check fails, retain remaining evidence and report the exact resources.
